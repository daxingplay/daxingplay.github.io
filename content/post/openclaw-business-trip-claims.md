## 前言

今年春节前后 OpenClaw 挺火的，我也一直想找一个足够真实、足够麻烦、又适合 agent 长期参与的场景来试试它到底能做到什么程度。

想来想去，我第一个想到的就是差旅和报销。

这个场景很适合“养龙虾”：它不是一次性问答，也不是简单生成一段文字，而是一堆持续发生的小事。日历里有出差安排，路上会产生票据，邮箱里会收到发票，回来以后要导出材料，最后还要提交到内部系统。每个环节单独看都不难，但连起来就很烦。

报销本身不复杂，但它特别烦：吃饭的小票、打车的行程单、酒店 folio、12306 的电子发票、Uber 邮件、香港的公交截图……每一样东西都不难处理，但它们分散在微信/Telegram、邮箱、相册、PDF、截图里面。等到真的要提交报销的时候，才发现自己需要重新回忆：这张票是哪一天的？在哪个城市？属于哪次出差？有没有原始凭证？文件名是不是能看懂？

以前我通常是把这些东西先丢到一个地方，等有空了再整理。结果就是，“有空”这件事情经常不会发生。

于是我开始尝试让 OpenClaw 帮我做这件事。最开始我以为这只是一个“票据识别 + 导出表格”的小工具，后来做着做着才发现，真正难的不是 OCR，也不是 CSV，而是要把一整条差旅报销链路连起来。

## 整体思路

这件事最后被拆成了几层：

1. **Trip planner**：从日历里自动识别商务出差，生成 trip map，知道哪几天去了哪里；
2. **Evidence intake**：从 Telegram、Gmail、手动文件里收集小票、发票、酒店 folio、行程单等证据；
3. **Trip matching**：根据日期、城市、票据类型，把证据归到对应的 trip；
4. **Evidence DB**：把原始来源、附件、解析结果、失败原因、去重 key 都存起来，而不是只写一个 CSV；
5. **Export + audit**：需要报销时，重新从证据库生成 claim 包，并检查缺失、归属错误、弱 key 等问题；
6. **最后一公里**：把整理好的材料提交到内部报销平台。具体流程敏感，不展示细节，但会用 API 分析和浏览器自动化完成。

所以这篇文章不是只讲“怎么识别一张发票”，而是记录我怎么把一个真实的差旅报销流程，一点点交给 OpenClaw 处理。

下面再展开讲每一层遇到的问题。

## 先要知道：哪几天算出差？去了哪里？

报销的第一步其实不是票据，而是行程。

如果系统不知道我哪几天在出差、在哪个城市出差，那它就没法判断一张小票应该归到哪次出差里。所以我们先做了一个 trip planner：从日历里自动抓事件，识别未来和最近的商务出差，然后生成一张“trip map”。

这里面也有不少细节。

一开始，检测逻辑看起来很简单：日历里有“出差”“Business Trip”“Business Travel”这样的多日事件，就认为是一趟出差；如果某一天有地点在杭州以外的会议，就认为是一天的出差。地点只信任日历事件的 location 字段，不从标题和备注里乱猜。这个原则后来证明很重要，因为标题里经常会有各种不稳定的信息，猜错一次，后面的票据匹配就全错。

后来又遇到一些真实世界的问题：

- CalDAV 返回的日历数据不完整，有些 ATTENDEE、STATUS、TRANSP 字段需要再 GET 一次完整 ICS；
- tentative、cancelled、needs-action 的会议不能算已经确认的出差，否则会凭空多出一趟行程；
- 同一个会议可能出现在多个日历里，需要优先使用 organizer 是自己的那份；
- 过去的出差不能因为最近一次同步没扫到就从状态里消失，因为报销经常是回来之后才做；
- 需要支持 backfill，因为日历可能后来才补，或者检测规则升级之后要重跑历史行程。

所以这个 trip planner 后来从一个简单 JSON 文件，演进成了 SQLite-backed 的 trip store。TypeScript 负责稳定地从 CalDAV/ICS 里检测行程，Python 的报销脚本通过同一个 SQLite 文件查询行程。这个决定我还挺喜欢：不用为了“统一语言”硬把已经稳定的 TS 检测流程重写成 Python，而是把集成边界放在数据层。

有了这张 trip map，后面的票据 intake 才有意义。否则收到一张 2026-04-22 的香港餐厅小票，系统并不知道它属于哪一趟香港出差。

## 票据入口：能随手丢进去，才会真的用起来

我给自己建了一个专门的报销入口，最常用的是 Telegram 里面的一个 Claims 话题。出差过程中，看到需要报销的东西，我就直接发进去：

- 餐厅小票，拍照发进去；
- 公交、地铁、打车截图，发进去；
- 酒店账单 PDF，发进去；
- 邮箱里的火车票、Uber、酒店邮件，让它定时去 Gmail 里面找；
- 最后需要报销的时候，告诉它导出某一次出差的 claim 包。

表面上看，这只是“把图片发给机器人”。但真正有用的是后面一串自动化流程：OpenClaw 会识别日期、城市、金额、商户、类别，然后按票据日期匹配到对应的出差，再把原始文件、规范化文件、结构化数据都存起来。

比如我在香港出差时，发过不少这样的凭证：KMB 公交截图、川菜馆小票、火锅店小票、Satay King 的餐饮小票、酒店账单等。它会把这些都归到同一次香港出差下面。最后导出的时候，生成一个 zip，里面有 `claim.csv`、原始凭证、审计报告，以及按日期和城市命名的目录。

这比“我自己记得整理”靠谱多了。

## 真正麻烦的是证据，而不是表格

一开始很容易把这个问题想成“生成一个 claim.csv”。后来实际做下来才发现，`claim.csv` 不能作为唯一事实来源。

因为票据来源太多了：

- Gmail intake；
- Telegram topic intake；
- 手动文件；
- repair 时重新从 Gmail 扫出来的附件；
- 酒店 folio 和发票来自不同邮件，但实际上属于同一笔酒店费用；
- 同一张发票可能邮件里有 PDF、OFD、XML 多个附件。

如果每个入口都直接往某个 trip 的 `claim.csv` 里写一行，后面就很难修。错了不知道是谁写的，重复了不知道怎么合并，parser 升级之后也不知道哪些旧数据应该重新跑。

所以后来我们把证据层重构成了一个全局 evidence DB。它区分两个概念：

1. source identity：这个输入来自哪封邮件、哪条 Telegram 消息、哪个文件；
2. expense identity：它代表现实世界里的哪一笔费用。

这两个东西不能混在一起。因为同一笔费用可能来自多个 source，比如酒店 folio 一封邮件、发票另一封邮件；也可能同一封邮件里有多个附件。证据库会保存原始文件、附件类型、解析结果、失败原因、parser confidence、以及和 trip 的关系。`claim.csv` 变成导出时从 evidence DB 重新生成的产物。

这个设计解决了很多后来才会遇到的问题：

- 解析失败的 source 不会反复被处理，但以后 parser 变强了可以 repair；
- weak key 的票据可以先进入报销包，同时标记为 pending，后续再升级成更强的 dedupe key；
- audit 不只是检查“缺不缺文件”，还可以检查“这张票是不是属于这趟出差”；
- repair 不只是补东西，也可以发现历史迁移、staged 文件、Gmail index 里的不一致。

这部分听起来有点工程化，但我觉得这是从 demo 走向真实可用的关键。

## Gmail intake：比想象中难很多

国内差旅还有一个很常见的问题：很多正式发票其实不在相册里，而是在邮箱里。

比如 12306 的电子发票通知、Uber 的行程邮件、酒店的 invoice/folio。这些东西如果靠人手动找，会非常痛苦，因为你要在 Gmail 里搜不同关键词，再下载附件，再改文件名，再放到对应行程下面。

我现在让 OpenClaw 定时跑 Gmail intake。它会按规则搜索候选邮件，下载附件或解析邮件正文，然后尝试匹配到当前活跃的出差。

这块也不是一开始就完美。中间踩过不少坑：

- Gmail query 不能只用一个很窄的日期窗口，因为发票经常延迟开；
- 但 query 太宽又会污染别的 trip，所以后来又把搜索 scope 到特定 label、trip 起始日期、关键词组合；
- 12306 发票里有“红字”之类的字样，曾经误判成退款，需要重写 parser；
- Uber 邮件可能是转发格式，HTML 里还有营销文案，不能把 CTA 按钮当成上下车地点；
- 酒店 folio 有时是扫描 PDF，普通文本提取拿不到金额，需要 fallback 到 Gemini Vision OCR；
- Gmail 抓线程可能失败、超时，失败信息如果不落盘，下一次根本不知道卡在哪里。

后来我们把 Gmail intake 从“LLM 一步步调用 Gmail 工具”改成了一个 script-first orchestrator：批量搜索、抓线程、下载附件、确定性 parser、匹配 trip、写入 evidence DB，最后输出结构化 summary 和 review queues。LLM 只处理异常和修复，而不是每一封邮件都让它自由发挥。

这个方向也很重要：AI 不是替代所有 deterministic code，而是把确定性流程写成工具，再让 agent 去调度、审计、修补。

## 它不是魔法，还是会踩坑

我不想把这个体验写得像广告，因为真实情况并不是“AI 一上来就全自动解决报销”。

它会有很多小问题：

- OCR 环境缺工具时，图片只能先暂存，后面再补录；
- 有些票据本身拍得不清楚，识别结果需要人工确认；
- 邮箱抓取可能受网络、OAuth、超时影响；
- 不同国家和地区的凭证规则不一样，香港小票和内地电子发票就不是一套逻辑；
- `claim.csv`、证据库、导出 zip、审计报告之间的关系，一开始也需要设计清楚。

但我反而觉得这些坑很有意思。因为这说明它不是一个“问答机器人”，而是在逐渐变成一个能处理真实杂事的个人系统。

以前我对 AI 助手的想象，经常停留在“帮我写一段文字”“帮我总结一下网页”。这些当然有用，但还不够贴近日常生活。报销这件事的价值在于，它打通了很多零碎环节：日历、聊天、图片、邮箱、文件、数据库、导出、审计、提醒。

当这些环节连起来以后，AI 才真的开始像一个助理。

## 最后一公里：提交到内部系统

导出 zip 之后，还有最后一步：提交到公司的内部报销平台。

这部分比较敏感，所以我不会在这里展示具体平台、接口和流程。但思路可以讲一下。

很多内部平台没有公开 API，至少不会专门给个人自动化用。我的做法是：先在浏览器里正常操作一遍，抓出真正有用的几个 API 调用，然后让 agent 理解这些请求的结构、字段含义和前后依赖。能直接用 API 调的部分，就让它调用；不能直接调的部分，就回到浏览器自动化。

这里也踩过坑，尤其是文件上传。很多上传流程不是简单 POST 一个文件就结束，它可能有临时 token、预签名 URL、前端状态、附件和表单行的绑定关系。最后有些步骤还是要让 OpenClaw 的 browser skill 真的去点按钮、选择文件、上传，再检查页面状态。

这也是一个很现实的经验：内部系统自动化不是“有没有 API”这么简单，而是要能在 API、浏览器、文件系统之间切换。agent 的价值不是只会写 HTTP 请求，而是能理解整个流程，必要的时候像人一样操作浏览器。

## 一个让我印象很深的细节

有一次我让它重新导出 2026 年 3 月 23 日那天的报销材料。它重新跑了一遍导出脚本，生成了 zip，审计结果是 0 个 error，只有 1 个 source pending 的 warning。然后它把 zip 发回给我。

这件事本身很小，但体验很特别：我不是在一个个文件夹里找东西，也不是打开 Excel 对着小票复制粘贴，而是直接说“重新导出这天的报销材料”。

这就是我想要的工作方式。

## 小结

这套东西现在还在继续打磨，肯定还有很多地方可以改，比如更好的 OCR、更稳定的 Gmail intake、更自然的人工确认流程、更适合公司报销系统的提交方式等。

但它已经让我明显感觉到，个人 AI 助手最有价值的方向，可能不是一次性回答一个问题，而是长期陪你维护一套工作流。

报销只是一个例子。它背后的模式是：

1. 从日历里知道未来和历史的 trip map；
2. 真实世界里产生一堆零散证据；
3. 你用最低成本把它们丢给助理；
4. 助理负责结构化、归档、匹配、审计；
5. 需要交付的时候，生成一个人类可审核的结果；
6. 最后一公里，再通过 API 或浏览器自动化提交到系统里。

这听起来不炫酷，但非常实用。

我现在越来越觉得，好的 AI 助手不应该只是“聪明”，还应该“可靠”。它不一定每次都能立刻给出完美答案，但它应该能记住上下文，保留证据，承认不确定性，并且在出错时留下足够的线索让人修。

如果能做到这些，它就已经不只是聊天框了。
